# Bug found: London calendar uses inconsistent Day.js UTC state

The reported **previous-month heading and shifted calendar cells** reproduce in a real Vite/React/MUI DateTimePicker using Day.js 1.11.13 and MUI 7.23.3, with a Europe/Paris host timezone. London’s winter zero-offset conversion changes Day.js to UTC mode without rebuilding its local-mode backing Date. Cloning then changes its calendar fields. MUI clones while formatting the heading and advancing calendar days, exposing the inconsistency.

This is a narrowed reproduction: January 1 occupies the usual Thursday **position**, but the weekday headers themselves also shift, so it is not literally labeled Thursday. The original English screenshot likewise shows `S S M T W T F`, with 1 under W. The report’s wording and image are not fully consistent.

## Observed results and challenges

### H1 — host timezone matters
Prediction: timezone conversion interacts with MUI’s start-of-week/day generation; compare London with Paris/Riga/UTC across host zones.

**Result:** all 32 popups rendered without page errors (`evidence/browser.log`, `evidence/browser.json`). With January 7 noon input:

| Host | Target / construction | Heading | First visible 1, zero-based column |
|---|---|---|---|
| Europe/Paris, Asia/Kolkata | London, either reported construction | December 2024 | 4 |
| Europe/Paris, Asia/Kolkata | Paris or Riga, either construction | January 2025 | 3 |
| UTC, America/New_York | London, either construction | January 2025 | 3 |
| Europe/Paris | `UTC` via `.tz('UTC', true)` | December 2024 | 4 |
| Europe/Paris | `timezone="UTC"` prop | January 2025 | 3 |

The last pair is important: the MUI UTC prop uses `.utc()` rather than this named-timezone conversion route. “Any GMT timezone always fails” is too broad.

### H2 — cached fields disagree with a clone
Prediction: `startOf('month')` has January fields, but cloning it reads the backing Date in UTC and produces December fields.

**Result:** `TZ=Europe/Paris node experiments/module.cjs` verifies:

```text
month.format():       2025-01-01T00:00:00Z
month.$d ISO:         2024-12-31T23:00:00.000Z
month.clone().format: 2024-12-31T23:00:00Z
both valueOf():       1735689600000
```

The UTC-host control has no format discrepancy. An initial assertion wrongly predicted a changed timestamp too; it failed (exit 1, retained in `evidence/module-paris-initial.log`). UTC `valueOf()` compensates for the stored local offset, so the corrected test asserts equal timestamps but different formats and exits 0. This correction does not conceal the original error.

### H3 — isolate the zero-offset keep-local-time branch
Prediction: replacing only calls to `utcOffset(0, true)` with the existing `.utc(true)` operation should normalize the backing Date and remove the failure. Other calls are forwarded unchanged. This is a causal diagnostic, not a production repair or a copied date algorithm.

**Result:** `evidence/controls.log` and `evidence/controls.json` contain 12 fresh-context configurations: 2 hosts × 2 targets × original/diagnostic/original. On the failing Paris-host/London-target input `2025-01-01T18:30`:

| Run | Backing Date for month start | Heading | First week |
|---|---|---|---|
| Original | Dec 31, 23:00Z | December 2024 | blank, blank, blank, blank, 1, 2, 3 |
| Diagnostic | Jan 1, 00:00Z | January 2025 | blank, blank, blank, 1, 2, 3, 4 |
| Original again | Dec 31, 23:00Z | December 2024 | blank, blank, blank, blank, 1, 2, 3 |

Paris-target and UTC-host controls remain correct with and without the diagnostic. Screenshots: `evidence/control-original.png`, `evidence/control-diagnostic.png`.

The fixed-clock control initially failed an assertion expecting the exploratory duplicate-Sunday header. Under the January clock, original headers instead read **Saturday through Friday** (`evidence/controls-initial.log`); corrected prediction and rerun pass. The month/cell failure is unchanged. Header generation uses *now*, whereas cells use the selected month; differing seasonal offsets explain why header details need separate qualification. No exact historical-header match is claimed.

The traced adapter records an actual picker call `formatByString(monthStart, 'MMMM YYYY')`: input fields January 1 midnight, backing Date December 31 23:00Z, returned string **December 2024**. Its `getWeekArray` call records first-week cached dates **29, 29, 30, 31, 1, 2, 3**, showing the duplicated first date that moves 1 to index 4. The wrapper only observes calls.

### H5 — older reported Day.js
Prediction: Day.js 1.11.5 may have a different zero-offset implementation but still yield the wrong month/cells.

**Result:** with MUI 7.23.3, London shows December 2024, Saturday→Friday headers and an entirely blank first row; Paris shows January and correct headers/cells. `evidence/old-version.log` / `.json` retain this counterexample to identical rendering across versions. ## Why this is a bug, and remaining limits

The pinned official MUI documentation (`env/mui-source/docs/data/date-pickers/timezone/timezone.md:11-38`, headings **Overview** and **Supported timezones**) supports AdapterDayjs and IANA zones, derives the render timezone from the value, and supports explicit `timezone`. It warns support is ongoing, but does not specify wrong-month headings or clone-dependent date fields as intended behavior. The January input date and contradictory December heading, backed by actual clone inconsistency and narrow causal controls, establish an implementation defect rather than an ordinary UTC-to-local date change. This is not a claim that every displayed hour remains unchanged (the original-control screenshot shows 05:30 PM).

The investigation answers the narrowed report on the stated latest package pair. It does not establish the reporter’s host zone, exact disabled-date behavior, all GMT zones, all seasons, MUI 6.14 behavior, or literal “January 1 labeled Thursday.” No full upstream test suite or production build was claimed. For exact historical-screen matching, next obtain the reporter’s `start` value, host timezone, locale and complete picker props, then rerun in Chrome 118/macOS. Those missing details do not block the demonstrated defect.
