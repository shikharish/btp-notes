# B1841570 — nested Map values are not deep cloned

## Verdict
**VERIFIED_END_TO_END; exact report match.** In the public `_.cloneDeep` pipeline of lodash 4.6.1, the outer Map is new but both inner Maps are the originals. Mutating an object reached through the supposed clone mutates the original. Plain nested objects clone independently. This is not misuse of `cloneDeep` and is broader than nested Maps: direct object values of a Map also remain shared.

Tested on Node v26.12.0, npm 11.20.0, native JavaScript Map, Linux. The report used lodash 4.6.1 in JSBin, but browser/engine and any lockfile are unknown; this is a reconstructed environment, not that browser session. Git tag 4.6.1 resolves to commit `ddf9354d26f55ac4e8402b71770aaeac8ac6f093` (annotated tag object `f5f152d28d26653e808c6bd58807bc6689660b7e`). Both the tagged source `repo/lodash.js` and the independently acquired npm 4.6.1 main bundle `env/npm-4.6.1/package/lodash.js` reproduce the same result. The package declares that entry point at `env/npm-4.6.1/package/package.json:8`; the reporter harness explicitly loads the supplied file (`experiments/reporter-oracle.js:4`). Their file hashes differ, so they were tested independently (`evidence/reporter.txt`).

The saved trace sees only the root Map and its enumerable `extra` property, not entry values; the self-entry targets the original (`evidence/mechanism.txt`).
- **Decisive controls:** `python3 experiments/make-intervention.py` generates a separate diagnostic copy; `node experiments/mechanism.js lodash-intervention.js patched` checks recursive entry population after stack registration. Entries become visited, mutations isolate and cycles resolve to clones, while entry counts, repeated-reference sharing, shallow clone and plain-object controls hold. ## Causal sequence
- **OBSERVED:** Public `cloneDeep(m3)` creates a different Map but returns the original `m1` and `m2` as values; their leaf objects are shared and a mutation propagates. `evidence/baseline.txt`, `evidence/reporter.txt`.
- **STATIC:** `cloneDeep` calls `baseClone(value, true, true)` (`repo/lodash.js:9523-9525`). Map is a cloneable tag (`repo/lodash.js:266-271`); `baseClone` initializes such objects via `initCloneByTag` (`repo/lodash.js:2371-2375`), whose Map case calls `cloneMap` without passing `isDeep` (`repo/lodash.js:5161-5162`).
- **STATIC:** `cloneMap` allocates a new Map, converts entries to `[key, value]` pairs, and reduces them into it (`repo/lodash.js:3850-3852`, `repo/lodash.js:1189-1197`, `repo/lodash.js:383-387`). Neither the pairs' values nor keys are cloned: `set` receives the original references. This is the earliest responsible divergence.
- **STATIC + OBSERVED:** After initialization, `baseClone` registers the Map in its stack and recursively visits enumerable own properties via `baseForOwn`, not Map entries (`repo/lodash.js:2377-2389`, `repo/lodash.js:2667-2669`). `cloneDeepWith` uses the same deep-clone implementation with a customizer (`repo/lodash.js:9553-9555`); its trace visits the root Map and its own `extra` property, but no entry value (`evidence/mechanism.txt`). A self-entry points to the original Map. Thus the shallow-copied values reach the public result unchanged.

## Controls and intervention
`experiments/mechanism.js` tests the real public API with a self-cycle, repeated references, a nested Map, a separate enumerable Map property, a plain-object control and shallow `clone`. In the original trace, Map entries are not visited while the own property is deep cloned. The generated diagnostic variant `experiments/lodash-intervention.js` (not original or npm source) starts deep Maps empty in `initCloneByTag` (`experiments/lodash-intervention.js:5168-5169`) and recursively populates their values *after* stack registration in `baseClone` (`experiments/lodash-intervention.js:2383-2390`), leaving keys unchanged. It is generated by the top-level replacement script `experiments/make-intervention.py:1-8`, `experiments/make-intervention.py:9-24`. Its trace visits nested entries, preserves entry counts, resolves the self-cycle and repeated references to clones, isolates mutations, and keeps shallow clone and ordinary-object controls unchanged. A separate exact-report `cloneDeep` test changes the two reported identity comparisons as predicted. The source checkout was never modified; rerunning the original demonstrates recurrence. See `evidence/mechanism.txt` and `evidence/reporter.txt`.

This intervention is **diagnostic only**, not a verified complete repair: key semantics, Map subclasses, Set behavior, symbols, customizers beyond the measured trace, and the full suite were not assessed. Sharing in the original happens to preserve repeated identity but points to original objects, not cloned ones. No online issue comments, fixes, later source, other cases, or prior answers were consulted; contamination/exposure: none.
