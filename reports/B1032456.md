# Bug found — skipped transform leaks a string to a number-typed refinement

**Zod 3.24.1 reproduces the original example exactly.** A failed refinement marks its result `dirty`, not `aborted`. The transform forwards that dirty string without converting it; the next refinement still executes on it, although its declared input type is `number`.

Continuing refinements after failure is documented behavior. The narrower bug is continuing **across a skipped type-changing transform with the wrong callback input type**. A strictly compiled number-specific refinement can consequently throw a `TypeError` through `safeParse` instead of producing a validation result.

## Experiments and decisive evidence

The predictions below describe the hypotheses checked by the retained scripts and logs; their pre-run authorship is not independently recorded.

### 1. Original example and static type

**Prediction:** z1 logs only r1; z2 logs r1 and r2, both strings; no transform logs occur. TypeScript accepts r2's input as number, rejecting assignment to string.

**Observed:** exact reported output in `evidence/reporter.log`:

- `z1.safeParse('123')`: `r1 123 string`; one custom `Invalid input` issue.
- `z2.safeParse('456')`: `r1 456 string`, `r2 456 string`; two custom issues.
- No `t1` or `t2` logs.
- `--strict` compilation passes with a number assignment and an `@ts-expect-error` string assignment inside an outer callback. The directive would fail compilation if that string assignment became legal.

### 2. Controlled callback matrix

**Prediction:** allowing r1 through restores numeric input to r2; all-pass runs all callbacks. Without an intermediate transform, continued refinements are legitimate same-type issue accumulation. A fatal issue, invalid base type, or pipeline boundary prevents the downstream refinement. Sync and async entry points agree.

**Observed:** all assertions pass in `experiments/controls.cjs`; `evidence/controls.log` records callback values/types and results for all 14 cases (seven cases × two entry points), with one logged execution of each.

### 4. Number-specific callback and recurrence

**Prediction:** using the inferred number normally (`n.toFixed(0)`) throws on the original failed-first-refinement path, but succeeds if r1 passes.

**Observed:** `experiments/number-method.ts` compiles strictly without casts or suppression. `evidence/number-method.log` records false → true → false first-refinement outcomes with all other inputs/callbacks fixed:

## Why this is a bug rather than just documented continuation

Historical official documentation supplies both sides of the distinction:

- `repo/README.md:2299–2301`, **Abort early**: refinements continue by default; fatal issues stop them. This supports the two-issue result for ordinary same-type chains, and directly answers the report's first question: a false refinement does not itself abort parsing.
- `repo/README.md:2165–2169`, **.refine / Arguments**: the validation function's input is the schema's inferred type. The actual string argument contradicts that promise and the compiled declaration.
- `repo/README.md:2236–2244`, **Relationship to transforms**, and `:2399–2409`, **Relationship to refinements** explicitly allow interleaving, with declaration-order execution. The latter wording should not be taken to mean transforms run after every failure; it does not justify calling a number callback on an untransformed string.
- `repo/README.md:2163` advises refinement callbacks not to throw. The number-specific refinement callback does not explicitly throw or cast away types: a normal operation on the promised number throws because the library supplies a string.

Historical tests inspected (not claimed to have been executed): `repo/src/__tests__/refine.test.ts:252–279`, **chained refinements**, expects issue accumulation; `:281–306`, **fatal superRefine**, expects stopping. `repo/src/__tests__/transformer.test.ts:199–216,217–233`, **short circuit on dirty** / **async short circuit on dirty**, covers failure before a transform but not a subsequent refinement across a skipped type-changing transform. Those individual policies explain the mechanism but do not establish that their unsafe interaction is expected.
