# B2110563 — Hindi month variants fail to parse

## Verdict
**VERIFIED_END_TO_END, exact report match.** Moment 2.27.0, tag commit `3e1a95b5ef0a505fec567c5b2290fd80e1da18f9`, run through the actual distributed `repo/moment.js` and `repo/locale/hi.js`, reproduces the reported full-array February invalid result and the reported four failed month tests. The reported single-format test failure is more specifically a **valid but wrong January date**, not necessarily an invalid Moment. Node v26.12.0, UTC; reporter's Node, dependency lockfile, OS and timezone are unknown. No extra npm dependencies were installed.

Report spellings फरवरी, सितंबर, नवंबर, दिसंबर differ from the configured full forms फ़रवरी, सितम्बर, नवम्बर, दिसम्बर. August and the configured forms work; the other eight report forms work. Evidence: `evidence/baseline.txt`. The report's proposed conclusion is supported for these inputs, but this does not establish that every Hindi spelling must be accepted.

## Causal chain
1. **OBSERVED + STATIC**: Locale only configures those exact long/short forms and enables exact month parsing (`repo/src/locale/hi.js:33-39`; shipped `repo/locale/hi.js:40-46`). Its `preparse` callback converts Hindi digits, not these spellings (`repo/src/locale/hi.js:75-79`; shipped `repo/locale/hi.js:82-86`), called by `prepareConfig` (`repo/src/lib/create/from-anything.js:42-44`; shipped `repo/moment.js:2948-2950`). `monthsRegex` selects the exact-parsing branch (`repo/src/lib/units/month.js:288-297`), and `computeMonthsParse` builds the regex from locale names (`repo/src/lib/units/month.js:318-325`, `repo/src/lib/units/month.js:339-344`; shipped `repo/moment.js:1179-1186`, `repo/moment.js:1200-1205`). `evidence/trace.txt` shows no match for each of the four reported forms and a match for each configured form. This is spelling mismatch, not a general failure to process Devanagari.
2. **OBSERVED + STATIC**: For `DD MMMM YYYY`, `configFromStringAndFormat` yields no MMMM input (`repo/src/lib/create/from-string-and-format.js:51-70`; shipped `repo/moment.js:2764-2783`). `addTimeToArrayFromToken` skips the month callback when input is absent (`repo/src/lib/parse/token.js:30-34`; shipped `repo/moment.js:851-855`), so the callback's `invalidMonth` assignment is never reached (`repo/src/lib/units/month.js:75-83`; shipped `repo/moment.js:938-946`). Flags record an unused token and input and `parsedDateParts=[2018,null,13]`. `configFromArray` defaults the missing month to zero, January (`repo/src/lib/create/from-array.js:79-86`; shipped `repo/moment.js:2618-2626`). `isValid` ignores unused tokens and leftover characters unless strict (`repo/src/lib/create/valid.js:12-31`; shipped `repo/moment.js:162-181`), so direct and one-element-array parsing of `13 फरवरी 2018` returns valid 2018-01-13. Strict parsing rejects it instead. See `evidence/baseline.txt` and the DD MMMM YYYY candidate in `evidence/trace.txt`.
3. **OBSERVED + STATIC**: For the original array, the legitimate-looking DD MMMM YYYY candidate is valid but has score 15 (5 leftover characters + 10 for unused MMMM). Later YYYY/MM/DD parses numeric pieces as `[2013,19,18]`, overflows the month and is invalid, but has score 7. `checkOverflow` rejects month 19 (`repo/src/lib/create/check-overflow.js:15-23`; shipped `repo/moment.js:2258-2266`). `configFromStringAndArray` computes scores at `repo/src/lib/create/from-string-and-array.js:37-43` (shipped `repo/moment.js:2879-2885`); its selection branch after any valid format only compares score and does not check the new candidate's validity (`repo/src/lib/create/from-string-and-array.js:57-61`; shipped `repo/moment.js:2899-2903`). The invalid lower-score candidate replaces the earlier valid one, producing `_f=YYYY/MM/DD` and `isValid() === false` as reported. See actual candidate instrumentation in `evidence/trace.txt`.

The first divergence is unavailable alternate locale spellings; the separate selector behavior explains why the full array gives an invalid numeric format rather than the incorrect January result. Regex truncation is contradicted by the null matches; selection alone cannot explain the one-format failure.

## Controls and interventions
- Baseline includes all 12 report cases, matching configured spellings, direct/one-array/full-array forms, and strict parsing. August and canonical February both succeed (`evidence/baseline.txt`).
- A process-local diagnostic preparse wrapper maps the four reported spellings to the locale's configured forms, preserving the original digit preparse. All 40 assertions pass across full array, direct, one-format array and strict, including canonical spellings, August, and Devanagari digits. Month tokens are consumed without leftovers and dates are correct (`experiments/intervention.js`, `evidence/intervention.txt`). This is a scoped diagnostic intervention, not an exhaustive or production-ready normalization policy; it changes input spelling and may match substrings.
- Independently requiring candidate validity in the selector's later branch changes the reported full-array result from invalid numeric format to valid DD MMMM YYYY, but it remains **January**, while canonical February and August remain correct (`experiments/run-selector.sh`, `evidence/selector.txt`). Thus selection-only intervention is not a complete fix.
- Both temporary shipped-file modifications were restored by shell traps. Fresh baseline output after each intervention is byte-identical to the original (`evidence/restoration.txt`, `evidence/restoration-after-selector.txt`); repository status was clean. The generated instrumentation is the `console.log` inserted by `experiments/run-trace.sh:11-15` immediately after score computation at restored `repo/moment.js:2885`; it is not original Moment source and does not alter branch conditions. It occupied line 2886 during tracing, shifting subsequent bundle lines by one. The normalization runs only in its Node process.
