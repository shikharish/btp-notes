# B2108550 — Bug found: date-dependent custom-rounding test

**The reported test failure is reproduced.** Moment 2.17.1's official `custom rounding` test assumes that subtracting 30 days, 23 hours and 59 minutes and calling `toNow()` always rounds to `in 30 days`. That assumption fails across February: the interval is first decomposed into calendar months and remaining milliseconds, then the month is converted back to an average day count. The day count supplied to `Math.floor` is about **33**, not 31.

The supported defect is **a calendar-dependent official test expectation**, not a broken implementation of `Math.floor` or a demonstrated promise that all relative-time calculations preserve elapsed days. Historical duration tests explicitly expect average month-to-day conversion. No production patch is claimed or required for this diagnosis.

## Original observation and reconstruction

The report supplies Moment 2.17.1, Chrome 56/macOS, NZDT (UTC+13), and client time `2017-03-09 10:49:01`. Its single failure is:

- Test: `relative time:custom rounding`
- Assertion: `Round down towards the nearest day`
- Expected: `in 30 days`; actual: `in a month`

### Observed causal chain at the reported instant

1. The test sets `Math.floor`, day threshold `31`, and other unit thresholds, then constructs `a = moment.utc().subtract({days:30,hours:23,minutes:59})`.
2. With reconstructed now `2017-03-08T21:49:01Z`, `a` is `2017-02-05T21:50:01Z`.
3. `toNow()` calls `to(createLocal())`; `to()` creates a duration from the two moments. `momentsDifference()` aligns offsets, so the local Auckland endpoint does not introduce a timezone offset error.
4. `positiveMomentsDifference()` retains **one calendar month**, anchored at `2017-03-05T21:50:01Z`, plus **259,140,000 ms** (2 days, 23 hours, 59 minutes). February's month here is 28 actual days.
5. `as('d')` converts that stored month using `Math.round(146097 / 4800) = 30` days, then adds the remaining milliseconds. Result: **32.99930555555556 days**. The original endpoints are no longer consulted during this conversion.
6. `relativeTime()` floors that to **32**. Since `32 < 31` is false and the floored month value is **1**, it selects locale key **`M`**. English `M = 'a month'` and `future = 'in %s'` produce **`in a month`**.

The instrumented trace directly records the endpoints, month/remainder decomposition, converted day value, floored values and selected key. The hook, subtraction, offset-alignment, conversion formula and locale formatting links are established by source inspection; they are not separately instrumented.

## Controls and recorded results

1. **Calendar/timezone control:** March failed exactly as reported; January/April passed, in both timezones.
2. **Representation control:** under the same rounding/threshold settings a duration made directly from elapsed milliseconds produced `in 30 days`, while the endpoint-based duration produced `in a month` (`evidence/browser.jsonl`). This control is diagnostic, not a substitute reproduction.
3. **Decomposition comparison:** March retained one month and selected `M`; January retained zero months and selected `dd`/30 (`evidence/trace.jsonl`). Source inspection explains January's month-count decrement; the decrement itself was not logged.
4. **Threshold control:** changing only March's day threshold from 31 to 33 produced **`in 32 days`**, not `in 30 days`. Restoring threshold 31 restored `in a month` in the same browser. This confirms the inflated day value precedes branch selection; it is not evidence of a repair.
5. **Retained counterexample:** the May 8 endpoint **passed** despite retaining a month: its one April month converts back to 30 days, the correct calendar length in that case. The remainder is 86,340,000 ms, yielding 30.9993 days and `dd`/30. This rules out the broader explanation that retaining any month causes failure.

`experiments/trace.cjs` runs the historical library in Chromium with two observational logging injections: after `positiveMomentsDifference` computes its remainder and before `relativeTime$1` adds suffix arguments. Each replacement must match exactly once. The modified bundle is generated **in memory**, never written over upstream source. Its added logging lines are instrumentation, not upstream source references. March was observed failing twice in the unmodified baseline (different timezones) and twice in the diagnostic sequence around the threshold control; no timing/race claim is made.

## Conclusion and limits

**Bug found, narrowed to the official test's date-sensitive assumption.** A constant expected day string is incompatible with this live-calendar input and the historically tested duration conversion. The exact reported failure occurs through the original browser test and library artifacts, with the responsible state and branch demonstrated. Calling this simply “expected behavior” would overlook the actual reported defect: an official test fails because its supposedly clock-independent assertion is not valid throughout the year.

The available evidence does not establish that the library's approximate calendar-relative wording itself violates a public API promise. Chrome 56/macOS, the reporter's exact web page, its full-suite ordinal mapping, and its complete suite state were not recovered. Those limits do not block the narrower finding. No further step is needed to explain the reported failure; exact client-environment equivalence would require that original browser/page artifact.
