The reported stale placement class is a bug in reconstructed rc-trigger 1.10.4. After overflow moves the popup above its anchor, moving the anchor into sufficient space moves the popup below again but leaves its DOM class at topLeft. Popup.onAlign compares the returned alignment with the configured alignment, so it skips updating the cached class precisely when alignment returns to the configured placement.

Verdict: **Bug found**, narrowed to a continuously visible rc-trigger popup whose realignment returns from an overflow flip. Three repetitions, two return transitions each, reproduced the mismatch. No production source changes were made.

## Experiments and limitations

Experiment 1 hypothesis: a real rc-trigger with bottomLeft and adjustY=1 will produce topLeft when the anchor is near the viewport bottom, then physically return below when the anchor moves up while its DOM class remains topLeft. Prediction: callback points change bl,tl → tl,bl on overflow → room, but the second DOM class stays topLeft. Control: a fresh popup with sufficient room should have bottomLeft; disabling overflow should retain bottomLeft even near the bottom.

Experiment 1 result: reproduced in all three repetitions, including two overflow→room transitions per repetition. At anchor y=550, popup y=450 and points bl,tl with topLeft class. At anchor y=100, popup y=130 and points tl,bl, still topLeft class. Fresh-room control is bottomLeft; overflow-disabled control remains bottomLeft and extends below viewport at y=580..680. Initial setup errors: sandbox Chrome launch aborted; approved execution launched successfully. The first fixture used an incorrect .default CommonJS import; corrected the fixture import only, retaining the error log. Neither was counted as reproduction.

Experiment 2 hypothesis: inspecting the actual Popup instance immediately after each synchronous forceAlign should show stored topLeft while both configured and returned class calculations are bottomLeft after returning to room. Prediction: the exact comparison used by onAlign is false, explaining why it retains the old DOM class. This adds observation only; no library changes.


Experiment 2 result: confirmed. Every return transition recorded cached topLeft, equal configured/returned bottomLeft classes, false branch comparison, and a real popup below the anchor. On flipped transitions the comparison is true. Both controls still pass. No diagnostic source patch was needed.

Scope gap: the reported rc-select integration was not recreated because no rc-select version or original application was provided.
