# Lodash 4.13.1 `sumBy`: concatenation depends on the missing JavaScript input types

**Unresolved for the original report.** The text `640.0071.00` is reproducible with controlled string-valued `total_amount` properties, but the reported numeric literals return `711`. Lodash preserves each property and combines values using JavaScript `+`; historical tests explicitly require **no numeric coercion**. The narrowed string call is expected behavior, not a demonstrated Lodash defect. The report omits the database/driver and actual JavaScript types, so the original DECIMAL-to-`sumBy` failure cannot be adjudicated.

## Observation and scope

The original report calls `_.sumBy(sales, 'total_amount')`, identifies the database column as DECIMAL, lists `[640.00, 71.00]`, expects `711:00` (verbatim), and observes `640.0071.00`.

- With actual JavaScript **numbers**, the call returns numeric `711`; it does not reproduce the symptom. The displayed `[640.00, 71.00]`, if read as JavaScript literals, cannot preserve the trailing decimal zeros and contradicts the reported concatenated output.
- With string properties `"640.00"` and `"71.00"`, the exact reported text appears. Those quotes/types are a controlled substitution, not supplied facts about the reporter's rows.
- The database, driver, query, serialized rows, JavaScript property types, and runtime are absent from the report. No database pipeline was invented. Reproduction is narrowed to the supplied public Lodash call with controlled input types, not the reporter's unknown database-to-JavaScript conversion.
- The colon in the expectation is not a numeric formatting feature of `sumBy`.

**Observed diagnostic sequence** (`evidence/trace.log`):

1. `baseProperty('total_amount')` returns `'640.00'`, type string.
2. At index 0, `result` is undefined, so `baseSum` sets it directly to `'640.00'`.
3. The accessor returns `'71.00'`, type string.
4. At index 1, `result + current` produces `'640.0071.00'`, type string.
5. The numeric control follows the same branches, storing `640` then producing `711`.

Thus a database column's declared DECIMAL type is not inspected anywhere in this pipeline. The static shorthand dispatch and observed unchanged property/accumulator values connect input type to the exact output. Whether the reporter's driver actually returned strings remains unverified.

## Experiments: predictions, results, and challenges

1. **Input-type hypothesis (recorded before execution):** strings concatenate, numbers/conversion sum. Predicted the exact reported text for strings and numeric 711 for controls. Both official artifacts and both runtimes confirmed it. Function accessors preserved concatenation, excluding a shorthand-specific failure; mixed-type controls exposed the expected JavaScript `+` formatting differences.
2. **Historical intent hypothesis (recorded before execution):** the original numeric/property and explicit noncoercion tests should pass. `experiments/historical-tests.js` executes the unmodified `repo/test/test.js`, with QUnit's native filter `/sum methods|lodash.sumBy/`. Result: **13 tests, 14 assertions passed, 0 failures**, exit 0 (`evidence/historical-tests.log`). Both noncoercion tests actually ran. This is a relevant filtered suite, not a claim that the entire suite passed.
3. **Causal trace hypothesis (recorded before execution):** unchanged properties enter `baseSum`; first value seeds the accumulator and the second concatenates. Generated logging confirmed this, while numbers added normally. The variant keeps the original addition statement and introduces no conversion or branch repair. A final pristine rerun reproduced all original results (`evidence/pristine-rerun.log`).

Instrumentation mistakes retained: the first trace attempt rejected a nonunique replacement target because the same return statement also occurs in `getValue` (`evidence/trace-initial-failure.log`). The next attempt failed because `baseProperty` also runs during Lodash initialization, before the trace array existed (`evidence/trace-initialization-failure.log`). The final script scopes the replacement to `baseProperty`, initializes the logging array before module compilation, and resets it before each measured call. Neither setup error is the reported symptom. An initial custom QUnit `done` callback did not run because qunit-extras exits in its earlier callback; the harness now verifies test participation in an exit listener. No errors/assertions were suppressed.

## Decision and remaining boundary

The implementation's noncoercing behavior is historically intentional, not merely inferred from a passing reproduction. The numeric expectation would require numeric iteratee outputs; a database schema declaration does not guarantee those JavaScript types.

The previous documentation-only `bug_found` verdict did not answer the assigned report and is withdrawn. An unqualified numeric return annotation does not turn this demonstrated, explicitly tested noncoercing call into the reported arithmetic bug. No separate documentation defect is being substituted for the original claim.

**Final outcome: `unresolved`.** The gap is reporter-specific reproduction/input evidence, not the traced mechanism: the controlled string call is expected behavior, while the literal numeric call does not fail. In `result.json`, `reproduced: true` refers only to the exact concatenated text from the narrowed, controlled string-input public API call—not to numeric-input failure or a reproduced database integration.

To resolve the original report, obtain the database/driver versions, minimal query and returned rows, and `typeof sales[i].total_amount` immediately before the Lodash call (plus object/value-conversion details if not primitive). Then run that actual path on 4.13.1. The current evidence cannot infer those missing types from DECIMAL, identify or blame a driver, or establish a Lodash defect.
