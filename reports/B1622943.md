# Bug found: duration subtraction drops weeks and whole-second milliseconds

Day.js **1.11.19 reproduces all three reported failures**. Date subtraction consumes individual duration getters, but object durations retain their input units: weeks are never consumed, and milliseconds are reduced modulo 1000 without carrying the omitted whole seconds into the seconds component. The duration's total and ISO serialization remain correct.

The milliseconds claim needs narrowing: **500ms works; 1000ms is ignored; 1500ms subtracts only 500ms**. This is a duration-to-date integration defect, not evidence that the millisecond remainder getter itself is wrong.

Observed live values (`evidence/controls-published.log`, independently identical in `evidence/controls-source.log`):

1. `{ weeks: 2 }` has raw `$d={weeks:2}`, total **1209600000ms**, ISO **P14D**, `weeks()=2`, but `days()=0`. Subtraction invokes seven scalar additions, all zero; no week addition occurs. The date is unchanged.
2. `{ weeks:1, days:3 }` has total **864000000ms**, ISO **P10D**, but the only nonzero date operation is `add(-3,'d')`. Result: June 24 instead of June 17.
3. `{ milliseconds:1000 }` has raw `$d={milliseconds:1000}`, total **1000ms**, ISO **PT1S**, `seconds()=0` and `milliseconds()=0`. Again all date additions are zero. Whole-second milliseconds were not carried to another consumed component.

These observations connect input storage → getter results → actual scalar date operations → incorrect ISO output. The source's omitted weeks step and mixed raw/normalized component assumptions explain the losses; UTC parsing or ISO rendering does not.

## Why this is a defect

Historical public types explicitly support object durations containing weeks and milliseconds: `DurationUnitsObjectType` / `CreateDurationType` in `repo/types/plugin/duration.d.ts:18–25`, with `UnitTypeLongPlural` in `repo/types/index.d.ts:26`. `Dayjs.subtract(duration: plugin.Duration)` is an explicit overload at `repo/types/plugin/duration.d.ts:77–81`.

Historical tests also treat weeks/milliseconds as legitimate object components (`repo/test/plugin/duration.test.js:49–68`), numeric milliseconds as carrying into seconds (`:24–32`), and date subtraction by a duration as arithmetic on its components (`test('Subtract duration')`, `:220–228`). Those tests were inspected, not claimed as executed here. Nothing in this evidence supports silently discarding these accepted units. In the fixed UTC examples there is no calendar/DST ambiguity: a duration serializing as P14D or PT1S cannot correctly subtract zero. Equivalent numeric-duration inputs work.

## Experiment notes and challenges

**Experiment 1 — retained integration result:** the Vitest run produced exactly the report's three alleged failures, with seven passing controls, exit 1. This is consistent with different object/numeric-duration normalization.

**Experiment 2 — retained instrumentation result:** both published-package and generated-source logs show seven zero scalar operations for week-only and 1000ms objects, only days consumed from mixed weeks/days, and only the modulo-1000 remainder consumed for 1500ms. Numeric-duration reconstruction and numeric/unit subtraction preserve the tested small offsets. Full logs retain raw fields, totals, ISO strings, getters, arguments, and resulting dates for 11 cases.

**Unsupported chronology:** the earlier wording claimed hypotheses were recorded before execution and source inspection preceded Experiment 2. The retained scripts/logs do not independently establish that timing; these are evidence groupings, not a reconstructed chronological history.

Decisive challenges:
- **Not all milliseconds are ignored:** 500ms and 999ms subtract correctly; 1500ms subtracts 500ms. Negative 1500ms similarly adds only 500ms.
- `{ seconds:1, milliseconds:1000 }` loses one second; `{ seconds:1, milliseconds:500 }` works. This is not merely a week-unit issue.
- `{ days:14 }` works while equal-total `{ weeks:2 }` fails. Negative weeks also fail.
- `base.subtract(2,'weeks')` and `base.subtract(1000,'ms')` both work.
- `base.subtract(dayjs.duration(d.asMilliseconds()))` equals direct millisecond subtraction in every small-offset control. This is a diagnostic representation change, not a proposed general calendar-duration repair.
- The trace wrapper delegates unchanged to the original `add`; each traced result is asserted equal to an uninstrumented result. Published and generated-source case traces match exactly (excluding the target header). Both control commands exit 0; their PASS means the **predicted defective behavior and controls** were verified, not that the original expectations passed.
