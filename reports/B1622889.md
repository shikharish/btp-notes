# B1622889 — duration ISO input retains overflowing minutes

**Bug found: a reproducible documented API-contract mismatch in Day.js 1.11.19.** `duration('PT75M')` returns minutes **75**, hours **0**, and formatted `H:m` **`0:75`** in Firefox and Node. ISO parsing stores the supplied components without normalization; getters and formatting read those components. The total milliseconds are correct. Historical official documentation nevertheless promises minutes and the `m` token in **0–59**.

This finding does **not** establish that every ISO component must be normalized internally: an upstream test explicitly preserves oversized ISO hours during serialization. The verified defect is the contradiction between documented getter/format behavior and accepted ISO input; changing documentation rather than implementation could resolve that contract mismatch.

## Experiment notes and challenges

1. **Mechanism hypothesis:** ISO parsing retains components, numeric parsing decomposes. Predicted ISO PT75M=75/0/0:75 versus milliseconds=15/1/1:15 with identical totals. **Result:** confirmed, including 59/60 boundary and 61/70/75 inputs. This distinguishes a component representation failure from a total-duration calculation failure.
2. **Contract check:** historical docs promise bounded getters/tokens, while tests preserve oversized ISO serialization. The “Durations” explanation (`env/dayjs-website/docs/durations/durations.md:8–12`) cautions about context-dependent units such as years/days; it does not document an exception for minute overflow. Therefore mere preservation in serialization is not sufficient evidence for “Expected behavior” across the reported getters/format.
3. **Browser hypothesis:** pure component parsing should behave the same in Firefox and across timezones. **Result:** confirmed, six trials, actual release UMD scripts. `evidence/browser-install.log` shows two download progress sequences reaching 100%, but does not record timeout durations or extraction/cleanup outcomes. `experiments/setup.sh` retains the direct browser ZIP acquisition and `unzip` alternative; the Firefox log confirms execution through the explicit `env/firefox-manual/firefox/firefox` path. Setup was not rerun during this review.
4. **Preservation challenge:** the existing oversized-hours ISO assertion should pass despite violating documented getter/token bounds. **Result:** `experiments/upstream-controls.cjs` executes that exact assertion and the numeric bubbling assertions against the release; all pass. PT2777H46M40S preserves its string, hours=2777, format=`2777:46`. This is a focused execution of the cited assertions, **not** a claim to have run the full upstream Jest suite.
5. **Additional Node controls:** `{minutes:75}` also retains 75 (and formats `undefined:75` because hours are absent); `.clone()` and `.add(0,'ms')` of PT75M yield 15/1/1:15 without changing total milliseconds. These are secondary observations, not silently substituted reproductions or separately adjudicated bugs. No production patch was made.

## Boundaries and remaining uncertainty

The report's observable failure and source mechanism are established. The narrow **Bug found** conclusion is a verified getter/format documentation-contract defect. Historical evidence does not decide whether maintainers intended raw components for these APIs or whether implementation should normalize them; it does not justify treating the official range promise as nonexistent. Exact macOS/browser-build reproduction and a full project test-suite run remain unperformed, but neither is needed to establish this release's pure-JS contradiction. No next step is required for this narrowed finding. To settle intended repair policy would require an authoritative specification distinguishing serialization/component preservation from getter/token normalization.
