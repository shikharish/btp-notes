# B2109128 — Unresolved (locale-policy correctness)

## Conclusion
Moment 2.19.4's Australian English locale returns **1 (Monday)**, reproducing the report. Its locale file explicitly supplies `week.dow: 1`. The cited historical CLDR 32 data independently specifies **AU: sun**, corresponding to 0. This is a demonstrated locale-data mismatch, not an import failure or a getter/calculation defect. Reproduction, responsible source, and the CLDR mismatch are proved, but intended locale-policy correctness is not established. No concrete obligation to adopt CLDR's AU setting was found in the checked historical policy/docs/tests, so the discrepancy alone does not establish a bug.

## Observation versus expectation
The report's exact API sequence loads `en-au`, selects it, and asks `localeData().firstDayOfWeek()`. Actual: 1; requested: 0. The original report already supplied the suspected configuration discrepancy and CLDR excerpt. No issue comments, fixes, later implementations, or online explanations were consulted.

Historical evidence is not entirely one-sided: the pinned repository intentionally encodes Monday and its tests agree. `repo/src/test/locale/en-au.js:203–206` expects January 1, 2012 (Sunday) to remain week 52 and January 2 (Monday) to begin week 1. The harness re-expresses these expectations using UTC date strings (`experiments/reproduce.cjs:20–23`), and they pass; it does not execute the original test callback. Thus this is not a regression against the included tests. The report's explicit CLDR 32 reference, acquired independently as `cldr-core@32.0.0`, has `"AU": "sun"` at `env/cldr-core/supplemental/weekData.json:73`, but that does not itself establish Moment's obligation to use it. No claim of a universal cultural convention or mandatory CLDR compliance is made.

## Focused historical policy check
The follow-up hypothesis was that a historical locale policy might require the cited CLDR setting, which would make the mismatch a defect. Reading the pinned `repo/README.md` and `repo/CONTRIBUTING.md`, checking the locale/getter tests, and searching the pinned tree for CLDR references did not establish such a requirement:

- `repo/CONTRIBUTING.md:11` requires locale unit tests; `repo/CONTRIBUTING.md:56–63` requires approval by the original locale author or another native speaker for locale changes. It does not designate CLDR as authoritative or require matching its week settings.
- `repo/README.md:9` links external documentation; the file states no CLDR locale-data obligation. The live documentation was not treated as historical evidence.
- `repo/src/test/locale/en-au.js:203–209` expressly expects Monday-based week transitions. `repo/src/test/moment/locale.js:173–179` tests that the getter returns the configured value, not a value selected from CLDR.
- `git -C repo grep -n -i 'cldr' -- ':!CHANGELOG.md'` finds only Russian-locale comments and their generated copies, not a general locale policy or an Australian-week requirement.

These checks support the implemented configuration's intentionality, but do not settle the report's challenge to the correctness of that regional choice. Neither a passing test nor disagreement with CLDR resolves that policy question. Outcome changed to **Unresolved**, preserving the reproduction and causal evidence.

## Source cause
1. Original configuration `repo/src/locale/en-au.js:53–56` supplies `{dow: 1, doy: 4}` to `defineLocale`. The executed release locale has the same settings at `env/node_modules/moment/locale/en-au.js:59–62`.
2. `defineLocale` constructs the locale at `repo/src/lib/locale/locales.js:110`, using `mergeConfigs` (`repo/src/lib/locale/set.js:25–33`). `Locale` (`repo/src/lib/locale/constructor.js:1–5`) calls `set`, and `set` (`repo/src/lib/locale/set.js:6–16`) stores non-function properties under `_`-prefixed keys, giving `_week.dow = 1`.
3. Explicit `moment.locale('en-au')` selects this locale through `getSetGlobalLocale` (`repo/src/lib/locale/locales.js:66–83`). The no-argument `getLocale` returns that global locale (`repo/src/lib/locale/locales.js:161–169`). The executed public API bindings are at `env/node_modules/moment/moment.js:4495` and `env/node_modules/moment/moment.js:4501`. The public locale name in the recorded run confirms selection.
4. `repo/src/lib/locale/prototype.js:39–42` binds `firstDayOfWeek` to `localeFirstDayOfWeek`; that function (`repo/src/lib/units/week.js:49–51`, executed counterpart `env/node_modules/moment/moment.js:1270–1272`) returns `this._week.dow` unchanged. The run observes both public result and internal value as 1.
5. The consequence is also visible beyond the getter: a UTC date in midweek, 2017-12-13, starts its locale week on Monday 2017-12-11. `startOf` calls `weekday(0)` (`repo/src/lib/moment/start-end-of.js:31–34`), and `getSetLocaleDayOfWeek` uses `_week.dow` (`repo/src/lib/units/day-of-week.js:239–245`). Changing only `dow` in memory yields Sunday 2017-12-10, while retaining `doy: 4`.

Selected source and reference excerpts are saved in `evidence/source-excerpts.log`.

## Experiment notes and challenge
Before execution, the planned hypothesis was that the historical release returns 1 for `en-au`, 0 for default English, and that the locale-specific configuration is responsible. The initial plan was saved before acquisition. These predictions held.

The harness additionally tested a narrow causal intervention: change only `week.dow` with the real `updateLocale` API, expecting the getter and week boundary to change while `doy` stays fixed. They did. Restoring the original registered locale and reselecting it returns the getter to 1. This is evidence of responsibility, not a proposed production patch. Three historical test expectations were re-expressed against the distributed release (`experiments/reproduce.cjs:20–23`), using UTC date strings rather than the original local date arrays. This is a focused control against a runtime malfunction, not an unchanged execution of the repository test or full suite.

The first harness run had an instrumentation mistake: it expected `updateLocale('en-au', null)` alone to restore the *active global pointer*. It restores the registry but leaves that pointer on the modified object in this release (`repo/src/lib/locale/locales.js:132–158`, `updateLocale`; executed counterpart `env/node_modules/moment/moment.js:1921–1947`). The assertion failed after the successful reproduction/intervention (exit 1), retained in `evidence/reproduce-initial.log`. The harness was corrected to explicitly reselect `en-au` after unupdate. This is not evidence about the assigned defect. The corrected run and independent setup-script rerun both pass, with recurrence on the original locale and English controls before/after.

## Limitations

We did not run the whole historical test suite, assert anything about other locales, or investigate first-week-of-year (`doy`) correctness. Next action: obtain a contemporaneous authoritative Moment locale policy or requirement specifically governing AU week settings (or requiring the cited CLDR data). Without that evidence, defect status remains unresolved.
