# Finding: regression reproduced; Zod 3 support boundary unresolved

**Unresolved defect status, not unresolved reproduction or cause.** Zod 3.25.68 reproduces all four reported SDK-consumer compiler errors; 3.25.67 passes. With TypeScript 5.8.3's legacy **Node10** resolution, the application's `zod` import and the SDK's `zod/v3` import reach separate CommonJS and ESM declaration files for `ZodObject`. Their private `_cached` members have different declaration identities.

The previous **Expected behavior** classification is withdrawn: the general documentation's modern-resolver restriction is **not demonstrably applicable to legacy Zod 3**. Its own docs require TypeScript 4.5+, on which those modern choices cannot compile. A new mixed-import check passes on 4.5.5 for both releases, but fails on 5.8.3 only for .68. Historical library-author guidance supports the expectation of interoperation but does not settle this compiler/resolver combination explicitly. Neither an applicable exclusion nor a sufficiently specific obligation is established; patch semver alone does not decide the outcome.

This is a demonstrated compatibility regression—not conflicting installed peer-Zod versions or a runtime cache error. Modern-resolution probes remove this identity split, but the full SDK then has other errors.

## Causal path

1. The report's `module: commonjs` without `moduleResolution` selects **Node10**, confirmed by both full `--traceResolution` logs.
2. In 3.25.68, the root package `types` field is `./index.d.cts`. Its re-exports lead through `v3/index.d.cts` and `external.d.cts` to **`v3/types.d.cts`**.
3. SDK declarations `tool.d.ts` and `agent.d.ts` instead import `ZodObject` from **`zod/v3`**. Node10 does not honor the package's `exports["./v3"].types` mapping. Its physical-directory fallback chooses **`v3/index.d.ts`**, leading through `external.d.ts` to **`v3/types.d.ts`**.
4. Both files declare `ZodObject` at line 529 and a private `_cached` at line 530. The actual compiler program contains both declarations (`evidence/identity.json`). These are two declaration trees **inside the same installed zod@3.25.68**, not the SDK's `@openai/zod` alias.
5. TypeScript's `propertyRelatedTo` rejects private properties when their `valueDeclaration` objects differ, producing the reported `_cached` diagnostic. `tool` constrains parameters to the subpath `ZodObject`; `AgentOutputType` uses it too. The broader tool inference/depth diagnostics disappear together when the declaration paths are unified; their individual recursive inference internals were not separately instrumented.
6. In 3.25.67, root and subpath declaration wrappers converge on **`dist/types/v3/types.d.ts`** even under Node10. The identity probe finds only this one class declaration, and the full SDK consumer passes.

## Follow-up: applicable support boundary

**Hypothesis recorded before experiment 5:** TypeScript 4.5.5 cannot use the general page's modern resolver choices; its legacy Node resolver should fall back from the unrecognized `.d.cts` root `types` target to `index.d.ts`. The *mixed* root/subpath identity check should therefore pass on both releases, while 5.8.3 should reproduce the .68 split. Use strict mode, `types: []`, no suppression, and save actual compiler traces/declaration origins. Keep the SDK integration primary.

**Actual result:** confirmed (`experiments/support-boundary.cjs`, `evidence/support-boundary.json`, `evidence/support-boundary-summary.log`). The same four-line assignment fixture and ES2020/CommonJS/legacy-node options give:

| Compiler | Zod .67 | Zod .68 | .68 declaration origins |
|---|---|---|---|
| 4.5.5 | exit 0 | exit 0 | only `v3/types.d.ts` |
| 5.8.3 | exit 0 | exit 2, TS2322 `_cached` | `v3/types.d.cts` and `v3/types.d.ts` |

`evidence/support-4.5.5-3.25.68-trace.log:13–25` explicitly shows the root `types: ./index.d.cts` found, rejected as an **unsupported extension**, then `index.d.ts` selected. Lines 44–62 show `/v3` and the root's relative re-export converging on `v3/index.d.ts`. By contrast, `evidence/support-5.8.3-3.25.68-trace.log:13–17,27–31,32–45` selects root `.d.cts`, physical `/v3/index.d.ts`, and the root's relative `.d.cts` chain. Both controls use actual published Zod declarations, not copied types.

The actual 4.5.5 CLI rejects `node16` and `bundler` with TS6046 (exit 1); `nodenext` exists as an experimental option but emits **TS4124**, unstable/use nightly (exit 2). See `evidence/support-4.5.5-{node16,bundler,nodenext}.log`. A resolver-only control keeping `module: commonjs` also exits 2 with TS4124 explicitly on `moduleResolution` (`evidence/support-4.5.5-nodenext-resolution-only.log`); this is not merely an incompatible module choice. The baseline compiler's `verifyCompilerOptions` enforces this at `env/node_modules/typescript/lib/typescript.js:115761–115775`. Thus the modern choices are unavailable for a successful stable-baseline build, not simply absent from a newer configuration example. This checks Zod alone; the SDK and its transitive declarations were **not** claimed compatible with TS 4.5.5.

### Historical promises and exclusions assessed

All statements below are from the pinned .67/.68 source, not later policy or issue discussions.

- **General page context:** `repo/packages/docs/content/index.mdx:84–86` introduces examples with `zod/v4`; **Requirements** at 139–164 says tested TS 5.5+, then excludes legacy `node`/`classic`. It is an explicit restriction on that page, but it never says it overrides the separate legacy-v3 requirements. Its scope cannot simply be projected onto v3. The .67 page already has the same requirements (`evidence/intro-version-diff.log`), so the text is not evidence of an expressly changed v3 boundary in .68.
- **Version-specific requirements:** `repo/packages/docs/content/packages/v3.mdx:7–8,141–157,179,183–216` labels itself legacy Zod v3, requires **TypeScript 4.5+** and strict mode, assumes root imports and demonstrates object schemas. It neither states a modern-resolver requirement nor excludes later compilers' legacy-node mode. The root-only example and now the mixed identity fixture both pass at that baseline. This defeats a blanket claim that modern resolution is mandatory for v3, but does not itself test or explicitly guarantee every later compiler/resolver combination.
- **User/library interoperation:** `repo/packages/docs/content/basics.mdx:46–50` promises that Zod 3 remains exported at root **and** `/v3`, with bug fixes/stability improvements. `repo/packages/docs/content/library-authors.mdx:22–34` tells libraries to use a peer dependency so users can “bring their own Zod”; 64–78 recommends `/v3` as a permanent versioned import and discourages root imports **for library authors**, because root will change major. That is not a prohibition on v3 users following their root-import examples. Lines 80–98 say dropping Zod 3 support is not recommended, assert no breaking/code changes between 3.24 and 3.25, and show `acceptUserSchema(schema: z3.ZodTypeAny | z4.$ZodType)`. These are substantive compatibility guidance, not just semver. But the no-changes statement is about the 3.24→3.25 transition; it does not expressly specify declaration identity across both imports under TS 5.8/Node10. The library-author file is byte-identical in the .67 and .68 source trees (`evidence/library-author-version-diff.log` is empty).
- **Test countercheck:** `repo/packages/resolution/attw.test.ts:9–20,33–47`, test **“should run attw --pack node_modules/zod and check output”**, snapshots green Node10 results for root and `/v3`. This is evidence against treating every Node10 import as intentionally unsupported; it is not a mixed-type assignment test. `repo/packages/resolution/src/index.ts:1–15` imports/parses root and `/v3` separately; its build config uses bundler resolution (`repo/packages/resolution/tsconfig.json:3–6`). These tests were inspected, not executed, and do not establish the disputed identity guarantee.

**Assessment:** an applicable v3 legacy-resolver exclusion has **not** been established, so **Expected behavior is unjustified**. The docs give a reasonable integration expectation but leave the cross-version compiler/resolver support boundary ambiguous; no direct mixed-identity promise/test covering the failing configuration was found. The v3 baseline experiment passes rather than exhibiting a violation of that explicit baseline. Under the requested evidence standard, retain **Unresolved** rather than claiming either an established exclusion or a definite supported-obligation violation. The gap is expected behavior, not reproduction, source mechanism, or whether this is a regression.
