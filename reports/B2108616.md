# B2108616 — phantom offset from ISO date

**Verdict: VERIFIED_END_TO_END, exact report match.** On the actual Moment 2.18.1 shipped `repo/moment.js`, `moment('2015-01-01T00:00:00').utcOffset('2015-01-01T00:00:00').format()` returns `2014-12-31T12:00:00-01:00` in Australia/Sydney. Day 02 produces -02:00. `moment.parseZone` instead returns `2015-01-01T00:00:00Z`. See `evidence/baseline.txt`.

## Environment and oracle
Tag 2.18.1 resolves to commit `b8a7fc310eb3625e83fc0c8f1ea2840fa83c7378`; tag object and bundle hash are in `evidence/environment.txt`. Node v26.12.0, V8 14.6, tzdata 2026e, TZ=Australia/Sydney; no external dependencies used. Reporter used Chrome 56 on Windows in +11:00; that runtime is not reproduced. With TZ=UTC, the same phantom offsets appear but the displayed wall time differs, showing the erroneous offset does not require Sydney. A no-zone input should not yield a zone derived from the calendar date. The reporter compares parseZone, but the two paths do not have identical no-zone semantics: the setter normally preserves the instant, while parseZone's fallback preserves the wall clock as UTC.

## Causal sequence
1. **OBSERVED / STATIC** ISO construction correctly identifies no zone: the constructed local moment has `_f` `YYYY-MM-DDTHH:mm:ss`, `_tzm` absent, +11:00 and epoch 1420030800000 (`evidence/variants.txt`). The ISO regex declarations at `repo/src/lib/create/from-string.js:8-11` and `configFromISO` at `repo/src/lib/create/from-string.js:81-90` identify the timezone only from the separate ISO match group and construct the format accordingly.
2. **OBSERVED / STATIC** The subsequent string passed to `utcOffset` is handled independently by `getSetOffset` (`repo/src/lib/moment/prototype.js:126`, `repo/src/lib/units/offset.js:105-117`). It applies `matchShortOffset` to the *entire string*. The regex in `repo/src/lib/parse/regex.js:17` is global, unanchored, and permits a signed two-digit hour without minutes. It matches date segments `['-01','-01']`; `offsetFromString` chooses the last at `repo/src/lib/units/offset.js:50-63`, interprets it as -60 minutes. This is the earliest erroneous divergence, not a local timezone inference. The trace in `evidence/variants.txt` comes from a generated, instrumented copy of `repo/moment.js`, not logging present in the original bundle; it shows matcher, chunks and setter result.
3. **OBSERVED / STATIC** The setter records `_offset=-60`, `_isUTC=true` and adjusts the internal date with keepLocalTime unset (`repo/src/lib/units/offset.js:121-138`, `repo/src/lib/moment/add-subtract.js:27-40`). `valueOf` subtracts the stored offset (`repo/src/lib/moment/to-type.js:1-2`), so the instant remains 1420030800000; the formatter reads the -60 offset (`repo/src/lib/units/offset.js:19-32`). The displayed local time moves from midnight +11 to noon on the preceding day at -01. This is not an instant change.
4. **OBSERVED / STATIC** `moment.parseZone` is wired through the `createInZone` import alias (`repo/src/moment.js:21`, `repo/src/moment.js:67`); `createInZone` constructs locally then calls instance `parseZone` (`repo/src/lib/moment/moment.js:13-15`, `repo/src/lib/moment/prototype.js:129`, which binds `setOffsetToParsedOffset`). With no `_tzm`, it searches the original input with the longer `matchOffset` requiring hours and minutes for numeric offsets (also accepting Z) (`repo/src/lib/parse/regex.js:16`, `repo/src/lib/units/offset.js:173-185`). For this input there is no match, so it calls `utcOffset(0, true)`. Trace shows null and the resulting Z. This keeps the wall clock and changes the epoch to 1420070400000; the two APIs are therefore not literally equivalent here.

## How I reproduced and debugged it

1. Ran `TZ=Australia/Sydney node experiments/baseline.js`, then the UTC control. The malformed -01/-02 offsets persisted while wall-clock output changed with the host timezone.
2. Followed the public `utcOffset` binding into `getSetOffset → offsetFromString`, and compared that route with `setOffsetToParsedOffset` used by `parseZone`. The exact source and executed-bundle coordinates are below.
3. `node experiments/build-variants.js` created logging-only and diagnostic bundle copies. `TZ=Australia/Sydney node experiments/variants.js traced` recorded the matching regex, both `-01` fragments, the selected -60 minutes and resulting setter state. This used Node plus inserted logging, not an interactive/native debugger.
4. The intervention variant bypassed the false match for the narrowly tested no-zone input. Explicit-offset controls still worked; running `original` again restored the failure. `evidence/variants.txt` preserves these runs. Generated bundles were later removed, but their generator and logs remain; no unavailable generated line numbers are invented.

## Controls and intervention
- Explicit +11:00 and Z work, and epoch is unchanged by the setter; standalone +05 and full timestamp +05 also work (`evidence/baseline.txt`, `evidence/variants.txt`). The last genuine zone wins over date fragments.
- `experiments/build-variants.js:1-11` creates copies of the historical bundle. Its traced copy logs matcher, chunks, setter and parseZone fallback; the original and traced outputs agree. A second copy, built from the traced copy, retains instrumentation and adds one behavioral change to string-setter handling for the exact extended ISO seconds shape with no offset, routing it to the existing null/no-change branch (`experiments/build-variants.js:9-11`). It retains the +11 local offset and original instant, while all four explicit/short controls retain expected offsets and instants. The parseZone comparison is unchanged. Running original again restores the -01 result. Details and assertions are in `evidence/variants.txt` and `experiments/variants.js:6-14`.
- This is a deliberately narrow diagnostic intervention, **not a complete fix**: other no-zone ISO forms and API compatibility are untested. It does not force the setter to emulate parseZone's keep-wall-time fallback.
