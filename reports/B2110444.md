# Investigation B2110444

## Conclusion: Bug found — documentation; runtime is intentional
The original report's documentation complaint is established: the exact pinned official introduction promises local-mode behavior for ambiguous input, but the reported offset-free input produces fixed-offset-zero mode in Moment 2.26.0. This is a documentation bug, not a runtime offset-parser defect. The release's explicit historical test requires keeping the wall clock and changing to offset zero; intentional runtime behavior does not resolve the contradictory documentation promise.

### Focused scope check
The saved introduction at `evidence/docs-intro.md:13` defines ambiguous input as “without offset” and local parsing as local mode. Its upstream path is `docs/moment/01-parsing/00-intro.md` at the report-pinned momentjs.com revision `75f131855b96252b0d2ccaf2431c5ac929428a11`. `evidence/docs-intro.md:15` states exactly:
> `moment.parseZone()` keep the input zone passed in. If the input is ambiguous, it is the same as local mode.

The report's `2020-05-28T02:54:09` has no offset, so it meets that definition. In the saved actual-package New York run (`evidence/reproduce-new-york.log`), `moment(input)` returns `utcOffset() === -240` and `isLocal() === true`, whereas `moment.parseZone(input)` returns `0` and `false`. Their instants also differ (06:54:09Z versus 02:54:09Z). Thus “the same as local mode” is contradicted for both reported properties, not merely by terminology. UTC controls retain the mode difference even when numerical offsets coincide. The detailed parseZone page describes fixed-offset behavior, but does not retract or qualify the introductory ambiguous-input sentence; the historical tests establish runtime intentionality, not correctness of that sentence. The plain outcome for the original report as a whole is therefore **Bug found**, narrowed to documentation. No runtime change is requested.

## E1 result and historical expectation

A transparent wrapper around the real `utcOffset` method observes `[0,true]` for absent offset and `[-240,false,true]` for explicit offset; no library source was changed.

The pinned introduction really contains the reported local-mode promise (`evidence/docs-intro.md:13-15`). However the release test `repo/src/test/moment/zones.js:791-817`, named `parse zone without a timezone`, explicitly says “Not providing a timezone should keep the time and change the zone to 0” (`repo/src/test/moment/zones.js:800`). The detailed parseZone page at the same pinned docs revision describes fixed-offset mode (`evidence/docs-parse-zone.md:13`) and does not repeat the local fallback promise. This supports intentional runtime semantics and an inaccurate introduction, not an accidental runtime regression. The inaccurate official introduction is itself the established defect in the original report.

* `setOffsetToParsedOffset` at `repo/moment.js:3375-3387` (original `repo/src/lib/units/offset.js:187-199`) finds no parsed `_tzm` and no offset substring. * The real method trace records exactly that call. `getSetOffset` at `repo/moment.js:3302-3343` (original `repo/src/lib/units/offset.js:114-155`) sets `_offset = 0`, `_isUTC = true` and compensates for the initial local offset to preserve wall-clock fields; the decisive assignments/adjustment are at `repo/moment.js:3317-3324` and `repo/src/lib/units/offset.js:129-136`. The represented instant therefore changes from 06:54:09Z to 02:54:09Z in New York (four hours earlier); it is not merely a display-label change.
* `isLocal` at `repo/moment.js:3427-3429` (original `repo/src/lib/units/offset.js:239-241`) returns valid and not `_isUTC`. Consequently false follows directly; zero-offset local mode and zero-offset fixed mode are distinct even in UTC.
* With explicit -04:00, the `_tzm` branch at `repo/moment.js:3376-3377` instead calls `utcOffset(-240, false, true)` as observed, preserving that fixed offset. +05:30 likewise remains 330 minutes. These controls rule out general inability to parse or retain offsets.
