# Expected behavior: historical declaration-resolution incompatibility

## Conclusion
Both reported symptoms reproduce on a reconstructed July 2022 environment. They are explained by Deno's documented explicit module resolution, not a defective lodash `isNil` implementation or declaration. Historical Deno documentation explicitly warns that existing declaration files may be incompatible and recommends import maps. A two-entry map permits the original lodash runtime import and unchanged historical DefinitelyTyped declarations to check and execute successfully. The broad claim that there is no feasible way to obtain narrowing is not supported by these experiments.

## Observation versus expectation
The original report expects `@deno-types` pointing to DefinitelyTyped's lodash-es `isNil.d.ts` to enable nullish narrowing. Actual behavior:
1. With the override: declaration graph construction fails on bare import `lodash`.
2. Without it: checking a function parameter `string | undefined` fails TS2532 after `!isNil(value)`.
3. With explicitly mapped declaration imports: checking passes and string input prints `HELLO`; undefined input prints nothing.

The supplied issue is a capability request as well as a failure report. This conclusion is limited to the reproduced imports/narrowing, not a claim about all lodash APIs or all Deno versions.

## Causal explanation and source evidence
1. `experiments/exact.ts:1` overrides the runtime module's types. The resolved declaration (`repo/dt/types/lodash-es/isNil.d.ts:1-2`) imports `{ isNil }` from **`"lodash"`**, then exports it as default.
2. Deno's `resolve_import` (`repo/deno/core/module_specifier.rs:58-82`) implements explicit URL resolution: parsing `lodash` returns `RelativeUrlWithoutBase`; it has none of the allowed prefixes, so the function returns `ImportPrefixMissing` rather than resolving it against the referrer. `ModuleResolutionError::fmt` (`repo/deno/core/module_specifier.rs:40-48`) renders the observed diagnostic. `evidence/exact-check.log:2-3` identifies this declaration import and location. This is graph resolution failure before predicate checking, not lodash returning the wrong value.
3. Mapping only `lodash` loads the historical index, whose triple-slash references (`repo/dt/types/lodash/index.d.ts:13-24`) load the common declarations. Those import `../index` without an extension (`repo/dt/types/lodash/common/array.d.ts:1`, `repo/dt/types/lodash/common/lang.d.ts:1`). The next failure names the extensionless file URL and the array declaration import (`evidence/bare-only-check.log:2-3`).
4. Mapping that exact index URL to `index.d.ts` (`experiments/mapped.json:3-4`) removes the second resolution obstacle without changing code or declarations. Deno's `ImportMapResolver::resolve` delegates resolution to the map (`repo/deno/cli/resolver.rs:27-35`); `JsxResolver::resolve` uses `resolve_import` when no map is present and delegates to the map resolver otherwise (`repo/deno/cli/resolver.rs:66-77`).
5. The historical declaration already has the needed predicate: `LoDashStatic.isNil` at `repo/dt/types/lodash/common/lang.d.ts:987`, `isNil(value: any): value is null | undefined`. The mapped negative test's `wrong` function (`experiments/negative.ts:3-8`) sees **undefined**, not `any`, inside the positive `isNil` branch and rejects assigning it to string (`evidence/negative-check.log:3-6`). This proves that passing checks are not merely caused by disabled checking or erased types.
6. The original runtime implementation, `isNil` (`repo/isNil.js:21-25`), returns `value == null`; its byte-identical cached remote artifact is identified below. Checked mapped execution prints HELLO for a string and no output for undefined, consistent with that predicate.

## Historical expectation
- `repo/manual/typescript/types.md:3-9`: Deno uses explicit specifiers, not TypeScript/Node search logic.
- `repo/manual/typescript/types.md:34-50`: `@deno-types` replaces which module supplies types; it does not promise Node-style dependency resolution.
- `repo/manual/typescript/types.md:224-234`: declaration imports follow normal Deno import rules, so many web-hosted `.d.ts` files may be incompatible.
- `repo/manual/typescript/faqs.md:3-24`: non-Deno TypeScript may not work; import maps are explicitly suggested for extensions and bare specifiers.
- `repo/deno/cli/tests/testdata/error_type_definitions.ts.out:1` expects the same missing-prefix diagnostic for a declaration import (`baz`). This is intentional historical test coverage, not an unexpected crash.

Together these support **Expected behavior** rather than treating the behavior-changing import map as proof of a defect.

- Challenge, recorded before final controls: omit the extension mapping to isolate that dependency; deliberately assign a nullish-branch value to string to reject accidental `any`; run positive and absent arguments.
