# B1845523 — Bug found: `sumBy` contradicts its documented return type

Lodash 4.17.21 returns boolean `true` for `_.sumBy([{ bool: true }], 'bool')`, while its documentation says the result is a **number**. The first projected value becomes the accumulator unchanged; only later values undergo JavaScript addition.

**Verdict: Bug found — documentation/runtime mismatch.** This establishes the incorrect numeric-return promise, not that automatic boolean conversion is the only correct repair. Historical tests intentionally preserve nonnumeric results, so changing runtime behavior could break compatibility.

## Why the earlier verdict was wrong

The earlier report classified this as Expected behavior because historical tests require noncoercion. That explains the implementation but does not resolve its contradiction with the public return type. No explicit numeric-only projection precondition was found in the pinned documentation. The numeric-return complaint is part of the original report, not an unrelated documentation issue.

The reproduction and source explanation were correct; the classification was wrong. A read-only independent review of the original input, pinned docs/tests/source and focused rerun agreed with this narrower bug verdict. Previous verdict records remain in `evidence/pre-return-type-correction/`.

## Causal explanation

1. `sumBy` passes nonempty input and its resolved iteratee to `baseSum`.
2. `getIteratee → baseIteratee → property → baseProperty` resolves `'bool'` to an accessor returning the raw property value.
3. `baseSum` starts with an undefined accumulator. Its first defined projection is assigned directly: `result = current`. For a singleton boolean, the loop ends there and returns a boolean.
4. Additional projections use `result + current`. Two booleans therefore produce a number; string values can produce concatenation. Undefined projections are skipped, so longer arrays with only one defined boolean can also return a boolean.
5. The public return annotation still says `number`, without documenting that qualification. This is the demonstrated mismatch.

## Diagnostic intervention and limits

The original generated intervention converts boolean projections with `Number(current)` before accumulation. Singleton true/false become numeric 1/0; numeric, empty, string-only and undefined controls retain their results. Callback count stays three. Reloading the pristine source restores the boolean result and original hash (`evidence/trace-baseline.txt`, `evidence/trace-patched.txt`, `evidence/restoration.txt`).

This is not a production repair: `baseSum` is shared, and mixed boolean/string output changes from `truex` to `1x` (`evidence/compatibility.txt`). The documentation/runtime conflict establishes the bug; the intervention only verifies the responsible mechanism. Choosing a documentation change or compatible runtime change remains separate work. No boolean-specific historical normative test or shipped type declarations were found.
