# Finding: expected behavior for an unsupported direct conversion

**The reported Node.js symptom reproduces.** Moment 2.30.1 does not clone a Day.js 1.11.19 instance as a date. It treats it as a calendar-field object, ignores its `$`-prefixed internal properties, and defaults the missing fields to **today at midnight**. `moment(d.toDate())` preserves the original date.

**Outcome: Expected behavior**, narrowed to the supplied constructor reproduction. Historical documentation defines object input as calendar units with defaults and promises cloning for native Dates and Moment instances—not Day.js instances. No incorrect documentation promise of foreign-instance interoperability was established. This does not establish that the missing CSV application was otherwise correct.

## Observation and scope

The report expects `moment(dayjs('2026-03-01'))` to retain March 1, but observes March 19 (then today) in `Asia/Tokyo`. Its explicit `toDate()` conversion works. We executed that actual CommonJS pipeline using the reported library/runtime versions, not a substitute parser.

With the unmodified clock, this investigation observed:

```text
now: 2026-10-28T16:54:49+09:00
dayjs: 2026-03-01T00:00:00+09:00
moment(dayjs): 2026-10-28T00:00:00+09:00
moment(dayjs.toDate()): 2026-03-01T00:00:00+09:00
```

Fixing **only Moment's public `moment.now` hook** to `2026-03-19T17:09:56+09:00` produces exactly `2026-03-19T00:00:00+09:00`. This is a controlled reconstruction of today's date, not a claim that the machine clock or reporter's full environment was reproduced.

### Experiment notes and controls

1. **Object-routing explanation under test:** a foreign Day.js instance enters Moment's calendar-object path; missing recognized fields default to today. The earlier investigation notes predicted that direct conversion and `{}` would agree, while native Date, milliseconds, and Moment cloning would preserve March 1.
   **Observed:** the mechanism and supported conversions matched, but the `{}` prediction was imprecise. Literal `{}` returns the current **time**, because it is special-cased as undefined; a **nonempty unrecognized object** returns today's **midnight**, matching Day.js. This distinction is retained rather than hidden.
2. **Clock/input controls:** at each of two fixed clocks (March 19, 2026 and July 4, 2027), direct Day.js conversion and `{unrecognized:123}` followed today's midnight. Date, milliseconds, ISO string, Moment clone, and `{year:2026,month:2,date:1}` retained March 1. Adding those recognized own fields to a Day.js clone also retained March 1. A custom object's `valueOf()` was called **zero times**.
3. Direct inputs March 1, March 19, and March 1 at 08:15:30 all became today's midnight at both clocks. Thus the apparent “some inputs” dependence is explained: an input already equal to today can hide the discarded date. The original Day.js value remained unchanged.
4. **Instrumentation checks:** classifiers should reject Moment/Date identity, select the object branch, normalize to `{}`, produce seven undefined components, and fill today's Y/M/D plus zero time. Recognized own calendar properties should alter normalization/defaulting; native Date should bypass this path.
   **Observed:** exactly those events occurred. The direct case recorded:

   ```text
   classify: isMoment=false, isDate=false, isObject=true
   normalized: {}
   beforeDefaults: [undefined,undefined,undefined,undefined,undefined,undefined,undefined]
   currentDate: [2026,2,19]
   afterDefaults: [2026,2,19,0,0,0,0]
   output: 2026-03-19T00:00:00+09:00
   ```

   Native Date produced only the classification event, then March 1. Adding own calendar fields changed normalized input to `{year:2026,month:2,date:1}` and output to March 1. All three traced outputs matched the original bundle. These are observed values, not just static deductions. Months in these arrays are zero-indexed.

## Why this is expected, rather than a demonstrated library/documentation defect

Historical official documentation and release-local contracts support the constructor distinction:

- `env/moment-docs/docs/moment/01-parsing/06-object.md:9–20`, **Object**: input is `{unit:value,...}`; omitted units default to zero or the current date/month/year. `17-defaults.md:9–24`, **Defaults**, explains date/time defaulting.
- `env/moment-docs/docs/moment/01-parsing/12-moment-clone.md:9–17`, **Moment Clone**, promises cloning a **Moment**; `09-date.md:9–16`, **Date**, promises cloning a **native JavaScript Date**. Neither identifies foreign date-library instances as cloneable inputs.
- `env/moment-docs/docs/moment/01-parsing/01-now.md:4–9,13–25`, **Now**, explicitly documents `{}` returning now, consistent with the counterexample.
- `env/moment-source/moment.d.ts:357–390,441`, `MomentInputObject` / `MomentInput`, defines calendar-unit values and the supported Moment/Date/string/number/array/object input forms—not a general date-like `valueOf()` contract.
- `env/moment-source/src/test/moment/create.js:53–132`, test **object**, exercises calendar-field input; `:442–469`, test **defaulting to current date**, codifies the missing-field rule. These tests were inspected, not claimed as an executed full upstream suite.
- `repo/README.md:30,49` advertises the “same modern API” and a **“largely Moment.js-compatible API.”** This describes similar APIs, not shared instance identity or a promise that the separate Moment constructor will deserialize Day.js internals. The documentation wording was considered; no verified false conversion promise was found.

The trace therefore explains both the reported surprise and why explicit conversion works without showing a violation of the historical input contract. The dangerous silent acceptance of an unsupported object is real, but this evidence does not establish the requested direct interoperability as a promised feature.
